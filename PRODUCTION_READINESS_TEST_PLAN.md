# Production Readiness Guide & Master Test Plan
## Plugin: `local_qlogin_shomokh` (v0.6.2)

---

## 1. Key Recommendations Before Going to Production

Deploying an authentication, verification, and password-recovery subsystem requires extreme care. Follow these 7 golden rules before touching the production server:

### 1.1. Always Validate on a Clone / Staging Environment First
- Do **not** deploy directly to your production site.
- Create a staging instance with a cloned database and identical PHP, MariaDB/MySQL, and Moodle versions.
- Test the full flow on staging with real WhatsApp and email credentials before scheduling production deployment.

### 1.2. Execute a Full System Backup
- **Database Backup:** Complete `mysqldump` / `mariadb-dump` of the Moodle database.
- **Data Directory:** Backup of `$CFG->dataroot` (`moodledata`).
- **Codebase:** Backup of the Moodle code directory.

### 1.3. Secure Storage of API Keys and Secrets
- Avoid saving sensitive API keys directly in the database whenever possible.
- Place your secrets in `config.php` or environment variables:
  ```php
  // config.php
  $CFG->local_qlogin_shomokh_resendapikey = 're_live_xxxxxxxxxxxxxxxxxxxxxxxx';
  $CFG->local_qlogin_shomokh_resendwebhooksecret = 'whsec_xxxxxxxxxxxxxxxxxxxxxxxx';
  ```
- **Why?** Secrets stored in `$CFG` take precedence over database values and prevent exposure during database backups or accidental admin exports.

### 1.4. Resend DNS & Deliverability Prerequisites
- Use a dedicated subdomain for transactional mail (e.g., `mail.shomokalelm.com`).
- Verify **SPF** (`v=spf1 include:resend.com ~all`), **DKIM** (CNAME records generated by Resend), and set up a basic **DMARC** policy (`p=none` initially).
- Ensure the `resendfromemail` setting in Moodle matches an address under a **`verified`** domain in the Resend dashboard.

### 1.5. Meta WhatsApp Cloud API Subscription Check
- In Meta Developer Portal, ensure the Webhook Callback URL points to:
  `https://your-domain.com/local/qlogin_shomokh/webhook.php`
- **Crucial:** Confirm that your WABA (WhatsApp Business Account) has actively subscribed the Moodle App to the `messages` event. (Check `/{WABA_ID}/subscribed_apps` in Meta Graph API Explorer).

### 1.6. Moodle Cron Cadence
- Ensure the standard Moodle cron CLI job (`php admin/cli/cron.php`) is executing **every 1 minute** via crontab.
- Background email retries (`\local_qlogin_shomokh\task\retry_email`) and daily enforcement checks rely on cron.

### 1.7. Keep the Alternate Login URL Disabled Initially
- Do **not** immediately set the "Alternate login URL" in Moodle Site Policies.
- Install the plugin, run the diagnostics, link legacy aliases, and test via direct URL (`/local/qlogin_shomokh/index.php`) first.
- Only switch the global Alternate Login URL once all test suites pass.

## 3. Production Cutover Runbook

### Step 1: Pre-Flight Sign-Off
- [ ] All 9 Test Suites successfully completed and signed off on Staging.
- [ ] Production database and `moodledata` backup completed.
- [ ] Production Resend API key and Webhook secrets added to `config.php`.
- [ ] Meta WhatsApp Cloud API credentials configured and verified.

### Step 2: Code Deployment
- [ ] Upload `/local/qlogin_shomokh` to production Moodle.
- [ ] Log in as Administrator and complete the database upgrade via `/admin/index.php`.
- [ ] Open `/local/qlogin_shomokh/health.php` and verify all checks show **Ready (Green)**.
- [ ] Run the **Admin WhatsApp E2E Test** on production to ensure live Meta webhook connectivity.

### Step 3: Legacy Account Migration
- [ ] Open `/local/qlogin_shomokh/migration.php`.
- [ ] Review the dry-run scan and download the masked CSV report.
- [ ] Click **Link safe aliases**.

### Step 4: Activate Login Route
- [ ] Navigate to **Site administration > Security > Site policies**.
- [ ] Set **Alternate login URL** to:
  ```
  https://YOUR-DOMAIN/local/qlogin_shomokh/index.php
  ```
- [ ] Save changes.

### Step 5: Post-Cutover Monitoring (First 48 Hours)
- [ ] Monitor `/local/qlogin_shomokh/health.php` for failed email or WhatsApp events.
- [ ] Check Moodle Cron logs (`mdl_task_log`) for `\local_qlogin_shomokh\task\process_verifications`.
- [ ] Check server error logs (`/var/log/nginx/error.log` or `/var/log/apache2/error.log`).

## 4. Emergency Rollback Plan

If an unexpected critical blocker occurs after cutover:

1. **Immediate User Traffic Reversion (30 seconds):**
   - Go to **Site administration > Security > Site policies**.
   - Clear the **Alternate login URL** field (leave it blank) and save.
   - Standard Moodle login (`/login/index.php`) is instantly restored.

2. **Database State Preservation:**
   - Do **not** drop `local_qlogin_shomokh_*` tables immediately; all user accounts and enrolments remain completely safe because phone aliases do not mutate core `mdl_user` records.
   - If any accounts were suspended during testing, open `/local/qlogin_shomokh/health.php` or execute the scheduled task to automatically release all plugin-managed locks.
